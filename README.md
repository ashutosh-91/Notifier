# Notifier

A small ASP.NET Core service that receives notifications over HTTP and forwards an LLM-written message to
Discord when the notification is a warning or worse.

## How it works

```
POST /api/v1/notifications/receive
        │
        ▼
  level >= Warning ? ──no──▶ 200 OK (ignored, nothing sent)
        │ yes
        ▼
  rate-limit token available ? ──no──▶ 429 Too Many Requests
        │ yes
        ▼
  LLM classifies + writes the message ──fail──▶ 502 Bad Gateway
        │ ok
        ▼
  send message to Discord ──fail──▶ 502 Bad Gateway
        │ ok
        ▼
  202 Accepted
```

- Notification levels: `Info`, `Warning`, `Error`, `Critical` (forwarded when level ≥ `Warning`).
- The message body sent to Discord is the one generated by the LLM.
- Outbound sends are capped at **10 per minute** (token bucket).

## Configuration

Settings are read from the standard configuration sources (`appsettings.json`, `appsettings.{Environment}.json`,
environment variables, user-secrets). Keys:

| Key | Description |
| --- | --- |
| `Ai:BaseUrl` | OpenAI-compatible endpoint, e.g. `https://api.deepseek.com` |
| `Ai:Model` | Model name, e.g. `deepseek-chat` |
| `Ai:ApiKey` | API key for the LLM provider |
| `Ai:SystemPrompts:NotificationClassifier` | System prompt used to classify and write the message |
| `Discord:BotToken` | Discord bot token |
| `Discord:ChannelId` | Target Discord channel id |

The `Ai` section is **validated on startup** (`[Required]` + `ValidateOnStart`), so a missing/misconfigured
value fails the app immediately instead of at the first request.

> Secrets are not committed. Provide them via `appsettings.Development.json` (git-ignored), user-secrets, or
> environment variables.

## API

### `POST /api/v1/notifications/receive`

Request body:

```json
{
  "id": 1,
  "level": "Warning",
  "message": "Disk usage on web-01 is at 94%"
}
```

`level` accepts `Info`, `Warning`, `Error`, or `Critical`.

Responses:

| Status | Meaning | Body |
| --- | --- | --- |
| `200 OK` | Below the threshold — nothing forwarded | `{ "status": "ignored" }` |
| `202 Accepted` | Classified and forwarded | `{ "status": "forwarded", "message": "..." }` |
| `400 Bad Request` | Invalid payload (e.g. empty `message`) | ProblemDetails |
| `429 Too Many Requests` | Rate limit reached | ProblemDetails + `Retry-After` header |
| `502 Bad Gateway` | The AI provider or Discord is unavailable | ProblemDetails |

Error responses use the standard `application/problem+json` (RFC 9457) shape.

## Rate limiting

Outbound notifications are limited with a `TokenBucketRateLimiter`:

```csharp
TokenLimit = 5
TokensPerPeriod = 1
ReplenishmentPeriod = 6s      // => 10 tokens per minute
QueueLimit = 0                // fail fast; don't block the request
```

Assumptions (the spec only says "max 10 per minute"):

- The cap is **global and outbound** — it limits how many messages *this service sends*, shared across all
  callers. (The payload carries no client identity, so per-client limiting isn't expressible.)
- Exceeding it **drops** the message and returns `429` with `Retry-After`; nothing is queued. The check runs
  *before* the LLM call, so dropped notifications cost nothing.
- The bucket allows a small burst (up to 5) on top of the sustained 10/min rate.

## Testing

```bash
dotnet test
```

- **Unit tests** cover the level threshold, the outcome for each path (forwarded / rate-limited / dependency
  failure), the rate limiter, and the Discord request shape.
- **Integration tests** boot the real app in memory (`WebApplicationFactory`) with the AI and Discord
  dependencies replaced by recording stubs, and assert on real HTTP status codes (`200`/`202`/`400`/`429`/`502`).

## Design notes

- **Outcomes are returned, not thrown.** The service returns a `NotificationResult` (`Forwarded`,
  `NotForwarded`, `RateLimited`, `AiUnavailable`, `DiscordUnavailable`); the controller maps it to a status
  code. Rate limiting is an expected outcome, so it isn't modelled as an exception.
- **Interfaces at the boundaries** (`IAiProviderService`, `IDiscordClientService`) keep the core testable and
  make provider swaps easy.
- **Typed configuration** via `IOptions<Ai>` with startup validation.
- **Secrets stay out of source control.**

## Limitations

- Processing is synchronous — the caller waits for the LLM and Discord calls. For high latency you'd accept
  asynchronously (`202` + background worker + status endpoint).
- No retry/persistence: a dropped (`429`) or failed (`502`) notification is not stored or retried.
- Discord failures are surfaced (non-2xx throws) but there is no retry/backoff toward Discord.
